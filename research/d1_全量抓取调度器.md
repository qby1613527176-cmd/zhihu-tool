# D1 · 全量回答抓取调度器

> 2026-11-06 · 代码: `zhihu_tool/harvester.py` · 子代理超时,代码+一次完整实测已留下,主代理验收补写报告

## 核心发现：feeds 分页是 cursor 链，不是 offset

实测（子代理探测）：手工 bump `offset`（无 `session_id`）→ 服务器忽略，永远回第 1 页
（offset=0/100/500/1000/1400 全返回相同 first/last id）。
**必须沿响应 `paging.next` 链走**（内含 cursor + session_id + 页序号 offset）。

→ 这解释了浏览器通道深翻页停在 135 的原因（滚动触发链条中断），也指明了正道：
**直翻 paging.next，浏览器都不需要**。

## 断点续抓设计

SQLite 两表：`answers`（answer_id 主键去重）+ `state`（next_url/status/page0_ids 等）。
- 中断后重跑同命令即 resume（沿存下的 next_url 继续）
- session_id 过期（响应变第 1 页）→ 自动开新 session 从 0 重走，去重集合保证不重复入库，追到前沿后恢复正常

## 自适应节流（均值 ≥5s 硬约束）

- 基础 6.0s + 高斯抖动（σ≈1.2）；顺利一页 → 间隔 -0.2s 缓升（下限 5.0s）
- 空页/全重复/异常 → ×1.5（上限 30s），stall+1
- 连续 3 stall → 休眠 300s 原 URL 重试；再 stall → 硬停
- 40362/40301/429 → FastClient 内建指数退避；验证码/跳登录 → 硬停（禁自动重试）

## 实测战绩（question 19550225，标称 1528 回答）

```
answers=994 · pages=50 · status=done
next_url 链一路走到底(cursor+session_id),limit=20/页
```

**994 vs 1528 的差**：feeds 默认排序只暴露可分页部分；其余为折叠/隐藏/违规回答
（页面 answer_count 含水）。浏览器通道 135 → 调度器 994，深度 ×7，且全程无浏览器。

## 用法

```bash
python3 harvester.py 19550225            # 开抓/断点续抓
python3 harvester.py 19550225 --fresh    # 清空重抓
python3 harvester.py 19550225 --status   # 进度
```
