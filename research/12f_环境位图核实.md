# 12f · 环境位图核实：zhihulite 证据 + 我方沙箱实测位图

> 日期：2026-11-06 · 调研者：MOSS(T4v2 重派)
> 任务：核实「环境位图」假设——PoW 结果里是否编码了环境探针结果，导致沙箱 cookie 被 API 风控(40362)识别为假浏览器。
> **结论：假设成立，且比 12c 的预想更严重。** 位图机制被完整逆向实证；我方沙箱实测 w4 = `0x5C36~0x7C36`（真机 `0x4000`），zhihulite 实测 `w4=0x4030` 即被反标记——我们比那个已知必败值还多 5 个异常位。

## 1. TL;DR

1. **位图假设实锤**：`__zse_ck` 的 PoW 结果（record93，93 字符）前 48 hex 是 **12 个 16 位环境位图**，由 196 条 JS 环境守卫 + wasm 内 Go VM 的 16 条探针逐位置位。服务端解密后按位图判定会话可信度。证据来自 GitHub 项目 **zhihulite/zhihu_zse_ck**（2026-10-11 建，11-05 仍在更新）的完整逆向 + 真机对拍实测。
2. **w4 是决定性判据**（zhihulite 逐字段受控扫描实测）：
   - `w4 = 0x4000` → `302 → /people/zhihuadmin`（真实页）✅
   - `w4 = 0x4030` → `302 → /account/unhuman`（**token 有效、会话被反自动化层标记**）❌
   - w7、指纹值、UA 均不参与判定。
3. **我方沙箱实测**（harness 直截 `zse_ck_solver.js` 的 `makeSandbox` 跑守卫）：**w4 = 0x5C36（确定置位）~ 0x7C36（含异常位）**，6~7 个异常位。更糟的是：12c 设想的「setTimeout 的 toString 已修」**实际没修住**——node:vm 跨 realm 原型链坑使 prelude 的 patch 对宿主传入函数完全无效（详见 §5.1）。
4. **40362 映射**：zhihulite 只验证到挑战提交层（302 落点），全仓未提 40362；但「位图反标记 → unhuman 会话」机制已被实证存在，API 层 40362 与 /account/unhuman 是同一标记在两个出口的表现（12c H1 链条成立）。
5. **zhihulite 已纯 Python 静态算出过真页**（不跑 JS/wasm、零执行推常量），其还原件与我们当前 build（`a7d63cc5…`）**同源**——探针清单、守卫还原件、真机 profile 全部直接适用于我们。

### 2.2 它声称并实证了什么

README 原话：**"给一个 build 的 wasm，不跑它的代码、不跑 wasm、不读内存，直接用 Python 算出被服务端接受的令牌"**。算法全还原：

```
ck       = '005_' + radix64( encrypt_96( record93 + PKCS#7(3), rk, iv, mask ), alphabet, xreg )
record93 = <48 hex 位图> <32 hex 指纹> 'z' <8 hex crc32(UA)> <4 hex tail>
cookie   = __zse_ck = <ck 132 字符> + '-' + <meta 172 字符>
```

- 密钥材料（rk/alphabet/xreg/mask/iv）全部从当次 build 的 wasm **常量池静态推出**（rk = 常量池 #66..#97 逐条 `^0x7B7B7B7B`）；
- 位图与指纹是**固定环境常量**（profile 化，不换环境不用重算）；
- 实测：全新随机 build 多次，`302 → /people/zhihuadmin`（真实页）；不带 cookie 403。
- **边界（重要）**：① 验证终点是挑战提交层的 302 落点，**全仓 0 处提及 API 40362**——API 层是否同一判据未由它实证；②「换 handenv / 换 UA 后必须重新确认」位图与指纹；③ 每 build 常量轮换，整条流程必须一次抓取内闭环（ck 绑定 meta 指向的那次挑战的 build 常量）。

### 2.3 w4=0x4030 反标记证据（docs/BITMAP.md §5 + docs/ANALYSIS.md §6.1 原文）

> 逐字段扫描（同 build、同 meta，**只改位图**）：
>
> | 位图 | 落点 |
> |---|---|
> | `w4 = 0x4000` | `302 → /people/zhihuadmin`（真实页） |
> | `w4 = 0x4030` | `302 → /account/unhuman`（token 有效，会话被反自动化层标记） |
> | `w7 = 0x8000` 或 `0x8800` | 都通过（不参与判定） |
> | 指纹值、UA | 都不参与判定 |
>
> `w4` 的 bit5/bit4 来自 payload 层两条守卫：
> ```js
> if (setTimeout.toString().indexOf("native")  === -1) v6 |= (1 << 5);
> if (setInterval.toString().indexOf("native") === -1) v6 |= (1 << 4);
> ```

真机稳定位图（w1..w11）：`2000 1000 8000 4000 8000 8000 8000 8000 8000 8000 4000`（profiles/_live_fixture.json 的 record93 实测一致，w7 可为 0x8800）。

### 2.4 它的环境伪造手法（handenv.js 62KB + zseenv.cc）

1. **nativeFn（JS 层）**：给包装函数加**自有 `toString` 属性**返回 `function <name>() { [native code] }`——`fn.toString()` 直接命中自有属性，不走原型链。
2. **zseenv.cc（C++ node-addon，8493B）**：在原生侧替换 `Function.prototype.toString`，先查隐藏键注册表——防 `Function.prototype.toString.call(fn)` **绕过自有属性**（纯 JS 补不了的洞）；同时用 V8 API 造 **[[IsHTMLDDA]] document.all**（`typeof === "undefined"` 但可调用可索引，与 sdenv 的 `bin/documentAll.cc` 同一做法）。
3. **window.constructor 伪造**：`function Window() { [native code] }`（wasm 探针 #141 逐字验真，Object 形态即判 mock）。
4. **synth_stack.py**：`__b.zh` 第 2 段是 `btoa(Error().stack)`，真机是 16 帧 Firefox 形态模板（CVM/BVM/VM/syscall js 帧，域名全为 static.zhihu.com）——栈帧是提交内容，node 栈帧 = 泄漏。
5. 明确拒绝 jsdom/sdenv 整包，一律手写环境；`window/document/location/navigator` 全部只读（`writable:false, configurable:false`），载荷里 `window={};document={}` 在真浏览器是静默失败。
