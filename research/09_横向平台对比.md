# 09 · 横向平台反爬方案对比与知乎可移植思路（2025-2026）

> 调研日期：2026-11-06 ｜ 数据源：GitHub API（gh 认证查询，stars/更新时间为当日值）+ 实测探测（m.zhihu.com、news-at.zhihu.com）+ 关键仓库 README/源码抽查 ｜ 网络调用 ~19 次（预算 ≤20）

## 结论摘要

- **行业默认答案就是「真实浏览器 + 原生签名」**：NanmiCoder/MediaCrawler（70.2k★，2026-11-05 活跃）以 Playwright/CDP 复用真实浏览器登录态、在浏览器上下文里跑平台原生 JS 出签名，一套架构通吃小红书/抖音/B站/微博/贴吧/**知乎**，是当前事实标准。知乎方向我们不用另起炉灶，但可以在它基础上「减重」。
- **比它更巧的思路确实存在，且分三类**：① 找**无签名轻量入口**（微博 m.weibo.cn 移动站 JSON API 是教科书案例）；② 把**签名算法彻底文档化**做成纯 Python 免浏览器（B站 WBI 模式）；③ **借道官方旁路客户端**（微信公众号 → 微信读书 weread_mp 通道）。
- **对知乎的实测结论不乐观但有出口**：m.zhihu.com 已 301 到 www.zhihu.com（移动站 JSON 入口不存在，微博模式无法复制）；知乎日报 API（news-at.zhihu.com）实测连接失败，形同死亡；无公开数据开放平台。**但**知乎 Web API 的 x-zse-96/x-zst-81 签名社区已有成熟逆向、可纯 Python 化（B站 WBI 模式可移植），专栏页（zhuanlan.zhihu.com/p/）是 SSR HTML 可免签名解析，知乎小程序/App 通道是尚未排除的潜在轻量入口。

## 可移植思路清单

按「移植价值 × 落地成本」排序：

1. **【B站模式 · 最高优先级】把 x-zse-96 签名纯 Python 化，摘掉 nodejs/浏览器依赖**
   - MediaCrawler 爬知乎仍需 nodejs≥16 跑签名 JS，这是它知乎链路最重的依赖。B站 WBI 的历史证明：签名算法一旦被完整逆向并文档化，就可以变成纯 Python 函数（Miuzarte/Wbi 纯标准库实现是现成榜样）。知乎 x-zse-96 社区逆向已存在多年，**值得投入一次把算法钉死成文档 + 纯 Python 实现**，此后普通请求不再开浏览器。
2. **【微博模式】轻量入口枚举：知乎没有 m. 站，但有「专栏 SSR」这个半个例外**
   - 实测 m.zhihu.com 已 301 跳 www.zhihu.com，移动站 JSON API 不存在。但 MediaCrawler 源码显示其对 `/p/` 链接走 ZHIHU_ZHUANLAN_URL——**zhuanlan.zhihu.com 专栏文章页是 SSR HTML**，可直接解析免签名，适合作为「专栏文章正文抓取」的轻量通道（问答/评论仍需 API+签名）。
3. **【MediaCrawler CDP 模式】连接用户真实 Chrome 代替全新 Playwright 实例**
   - MediaCrawler 默认 CDP 模式 attach 到用户日常 Chrome（复用登录态/Cookie/扩展），官方明确说「大幅降低平台风控检测风险」。若 zhihu_tool 目前是干净 Playwright 实例，升级为 CDP attach 是低成本高收益的反风控改进。
4. **【Evil0ctal 模式】自愈身份池：cookie/账号多备份 + 失效自动轮换**
   - 抖音算法反不动就在运营层换身份。知乎同理：多 cookie 池 + 风控触发自动切换 + 授权过期提醒（we-mp-rss 也有过期提醒机制），把单点封禁变成可自愈的工程问题。
5. **【微信 weread_mp 模式】借道官方旁路客户端：知乎候选=微信小程序 / App API / RSSHub**
   - 微信读书证明了「官方另一个客户端的接口往往风控更松」。知乎对应候选：① 知乎微信小程序接口（抓包获取，历史上存在）；② 知乎 App 的 api.zhihu.com（部分端点历史上风控弱于 Web）；③ **RSSHub 知乎路由**——社区维护的同协议封装，可作现成数据代理层而非自建全部抓取。三者均需逐一实测验证，列入排查项。
6. **【反模式提醒】不要走的路**
   - 小红书式「selenium+fiddler 抓小程序包」：工程笨重、脆弱，只在无 Web API 时不得已为之；知乎有 Web API+已知签名，不需要。

## 知乎轻量入口排查（m站/小程序/开放平台）

| 候选入口 | 实测/现状（2026-11-06） | 结论 |
|:--|:--|:--|
| **m.zhihu.com 移动站** | 实测（iPhone UA）：**301 → www.zhihu.com**，返回桌面端 SSR 首页（145KB） | ❌ 已废弃，无微博式移动 JSON 入口 |
| **知乎日报 API**（news-at.zhihu.com/api/4/...） | 实测：连接失败（HTTP 000/超时） | ❌ 形同死亡，且只覆盖日报内容 |
| **知乎开放平台** | 官方开放平台面向品牌/商业内容合作（知+等），无公开数据读取 API | ❌ 对抓取无帮助 |
| **知乎 Web `/api/v4/*`** | 现役主通道：搜索 `/api/v4/search_v3`、评论 `/api/v4/comment_v5/...`、用户 `/api/v4/me`、主页 `/people/{url_token}`（HTML）；需 x-zse-96/x-zst-81 签名 + cookie | ✅ 主通道，签名可纯 Python 化（思路 1） |
| **zhuanlan.zhihu.com 专栏页** | SSR HTML（MediaCrawler 对 `/p/` 链接即走此域） | ✅ 半个轻量入口：专栏正文免签名解析（思路 2） |
| **知乎微信小程序 / App API** | 未实测，历史上有第三方抓包记录，风控强度未知 | ❓ 待排查（思路 5 的候选验证项） |

## 推荐行动

1. **短期（直接抄作业）**：zhihu_tool 接入/对齐 MediaCrawler 知乎模块的接口清单（search_v3 / comment_v5 / people），登录态方案升级为 **CDP attach 真实 Chrome**（思路 3），并加 cookie 池 + 过期提醒（思路 4）。
2. **中期（减重核心）**：立项把 **x-zse-96/x-zst-81 签名逆向固化为纯 Python 模块**（参照 Miuzarte/Wbi 的纯标准库做法），目标：常规读取请求零浏览器、零 nodejs（思路 1）。这是所有候选里对知乎收益最大的一件。
3. **低成本补充**：专栏类内容走 zhuanlan SSR HTML 直解析，不进签名链路（思路 2）。
4. **探索项（各 1-2 小时验证）**：抓包确认知乎微信小程序接口现状；实测 api.zhihu.com App 端点匿名/弱登录可用性；评估 RSSHub 知乎路由可否作兜底数据源（思路 5）。
5. **不做**：不考虑小程序抓包管道作为主路线；不等待知乎官方开放数据接口。
