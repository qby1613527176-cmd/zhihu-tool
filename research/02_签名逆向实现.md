# 知乎 x-zse-96 签名算法：开源逆向实现现状调研

> 调研日期：2026-11-06 ・ 方法：GitHub API（repo/issue search）+ raw.githubusercontent 源码直取 + shields.io 元数据（Web 搜索引擎在本机被拦，未用）
> 定位：我方方案（真实浏览器内让知乎自家 JS 签名）的对照组调研

## 结论摘要

- **算法本体自 2022 年起基本冻结**：签名结构 `"2.0_" + encrypt(md5("101_3_3.0" + "+" + path?query + "+" + d_c0 [+ body]))`，encrypt 为 **SM4 变体**（自定义 S 盒/轮常量、CBC、自定义 Base64 字母表）。RSSHub 内置的算法文件 2024-03 至今只有格式化提交、无算法变更；2022-08 的 CSDN 逆向文至今仍是标准参考。
- **逆向路线分两派**：① **纯算法端口**（Kotlin/Rust/Python/TS 重写，微秒级、零依赖，代表：zhihu-plus-plus 4.4k⭐ 血统）；② **跑官方 JS**（jsdom/execjs 经典派 → Node `vm` 沙箱新派，代表：HGXY2004/zhihu-proxy、cv-cat/ZhihuApis）。两派都活得好好的。
- **真正的活动层不是签名，是 `__zse_ck`**（2024+ 新增的混淆 VM + WASM PoW 挑战）和 IP 声誉风控。签名 4 年没动，挑战脚本在持续迭代。
- **维护成本结论**：纯端口派 4 年未被算法变更打破，但每次变更需重新逆向（熟手数小时～数天）；跑 JS 派对算法变更免疫（换 vendor 文件即可）但需维护浏览器环境模拟。两派维护成本都**显著低于预期**——但都不如浏览器原生签名免疫彻底。
- **建议**：维持浏览器原生签名为主力；可把公开纯 Python 端口（~200 行）作为轻量 fallback / 正确性对照；关注 zhihu-plus-plus 作算法变更预警雷达。

## 算法现状（2025–2026 在役版本）

### 请求头三件套（API 调用）

```
x-zse-93: 101_3_3.0                # 版本常量，多年未变
x-zse-96: 2.0_<加密串>              # 签名本体
x-requested-with: fetch
Cookie: d_c0=<设备指纹> [; z_c0=<登录态>]
```

另有 `x-zst-81`：仅在浏览器/滑块场景出现，直接请求 API 不需要；若存在则作为可选段并入签名 source（见下）。

### 签名公式（多源交叉验证一致）

```
source   = "101_3_3.0" + "+" + apiPath(含query) + "+" + d_c0 [+ "+" + body] [+ "+" + x_zst_81]
md5_hex  = md5(source)                       # 32 字符小写 hex
x-zse-96 = "2.0_" + encrypt_zse(md5_hex)
```

源头证据：srx-2000/spider_collection Issue #18（2022-02，知乎签名逆向经典讨论帖，26 条评论）中贴出的知乎官方 JS：

```js
s = [zse93, api_url, dc0, body?, xZst81?].filter(Boolean).join("+")
signature = encrypt(md5(s)); h.set("x-zse-96", "2.0_" + E)
// 官方 b 函数 = __g._encrypt(encodeURIComponent(e))
```

### encrypt_zse 内部结构（已从两个独立血统完整拿到源码）

- **分组密码**：SM4 结构变体——标准 SM4 的 L 线性变换（`X ^ rotl(X,2) ^ rotl(X,10) ^ rotl(X,18) ^ rotl(X,24)`）、32 轮、反序输出，但 **S 盒（256B）与轮密钥常量（32×u32）均为自定义值**（非国标 SM4 参数）
- **密钥混入**：首块 `plain[i] ^ KEY16[i] ^ 42`，KEY16 = ASCII `"059053f7d15e01d7"`
- **模式**：CBC（首块加密结果作为下一块 IV）
- **输出编码**：自定义 Base64 变体——字母表 `6fpLRqJO8M/c3jnYxFkUVC4ZIG12SiH=5v0mXDazWBTsuw7QetbKdoPyAl+hN9rgE`，逆序取字节、XOR 掩码 58 循环
- **输入预处理存在两个并存变体**（均输出 `2.0_` 前缀，双方项目均声称当前可用）：
  - **v3（RSSHub 血统，2022 起）**：直接对 md5 hex 的 32 个 charCode 分两块加密，无种子/填充
  - **v4 / "zse96 v2"（zhihu-plus-plus 血统，活跃维护中）**：`seed(12) + 0 + encodeURIComponent(md5hex) + PKCS#7 填充`，更贴近官方 `__g._encrypt(encodeURIComponent(e))` 行为
  - ⚠️ 两者密文不同，服务端疑似兼容（或 RSSHub 对部分端点已静默失效）。**参考实现以 zhihu-plus-plus 血统为准**（项目最活跃）

## 轮换历史与维护成本

### 头部字段轮换（社区共识时间线，部分未本次直接验证）

- `x-zse-86`：~2019 及更早的老签名头（2019 博客时代，本次未直接验证）
- `x-zse-91`：过渡版本（未直接验证）
- `x-zse-93`：现为**版本常量头**（值 `101_3_3.0`），不再承载签名
- `x-zse-96`：现役签名头，输出前缀 `2.0_`，**最早可考 2022-02**（spider_collection Issue #18），沿用至今 ≥4 年
- `x-zst-81`：滑块/浏览器场景附加参数，可选并入签名 source

### 稳定性证据（强）

1. RSSHub 的 `x-zse-96-v3.ts` 提交历史：2024-03-03（.js→.ts 改名）→ 2024-03-05 → 2024-03-06 → 2024-08-12 → 2025-06-23，**全部是 lint/格式化/重构，零算法变更**
2. 2022-08 的 CSDN 逆向文（126512798 / 126659351）至今仍被 RSSHub 官方文件信用
3. HGXY2004/README（2026-09）给出的公式与 2022 年 Issue #18 完全一致
4. 变化发生在**外围**：2024+ 新增 `__zse_ck`（混淆 VM + WASM PoW，`static.zhihu.com/zse-ck/v4/*.js`）与 `40362/40353` 风控码、IP 声誉层——**风控在迭代，签名算法没动**

### 两派维护成本对比

| | 纯算法端口派 | 跑官方 JS 派 |
|---|---|---|
| 代表 | zhihu-plus-plus → Rust/Kt/Py；RSSHub TS | HGXY2004/zhihu-proxy、cv-cat/ZhihuApis、spider_collection |
| 算法变更时 | 需重新逆向（S 盒/常量/前缀；熟手数小时~数天），4 年未触发 | 换 vendor 文件（分钟级），免疫 |
| 日常成本 | 接近零（无依赖、微秒级） | 维护浏览器环境模拟（window/document/navigator/cookie setter/WASM…），首次加载 ~100ms，单次 <1ms |
| `__zse_ck` 挑战 | 需另行求解（HGXY2004 已在 vm 中解出真 PoW `005_` 前缀值） | 同左，或靠浏览器 |
| 风险 | 知乎若换算法即失效（静默风险：v3/v4 两变体并存已现裂痕） | 官方包若加环境检测（canvas/WebGL/时序）则需补环境，对抗升级 |

## 与我们浏览器原生签名对比

| 维度 | 我方：真实浏览器让知乎自家 JS 签 | 逆向两派 |
|---|---|---|
| 算法变更 | **完全免疫**（知乎签自己的） | 端口派需重逆向；跑 JS 派换 vendor |
| `__zse_ck` WASM PoW | **天然通过**（浏览器自己跑） | 需额外模拟求解（可行但常新） |
| 环境检测/指纹 | **天然通过** | 补环境对抗，猫鼠游戏 |
| 单次签名成本 | 浏览器自动化开销（~秒级页面生命周期） | 微秒~<1ms |
| 资源/扩展性 | 重（每实例数百 MB 内存） | 轻（纯端口可嵌任何进程） |
| 失效模式 | 几乎只有 UI 改版 | 算法变更 / 挑战升级 / 环境检测 |
| 历史维护频率 | — | 签名层 4 年 0 次；挑战层持续小迭代 |

**互补判断**：逆向派的优势（轻、快、可嵌入）恰是我方短板；我方的优势（对签名+挑战+指纹三层全免疫）恰是逆向派长期风险点。历史数据显示签名层变更频率极低（≥4 年未动），所以逆向路线**并非不可行**，只是「省下的资源」与「承担的静默失效风险」之间的权衡。

## 推荐行动

1. **主力不变**：继续浏览器原生签名方案——它是唯一同时免疫签名算法、`__zse_ck` PoW、环境指纹三层机制的路线。
2. **低成本上保险（可选，~半天）**：把 Starzzb/zhihu-zse96-v2-python 的纯 Python 端口（~250 行、仅标准库、常量表完整）拷进来做 **fallback + 离线正确性对照**：平时可对同一 (url, d_c0) 同时用浏览器签名与本地端口签名比对，作为「算法是否变更」的金丝雀。
3. **预警雷达**：watch [zly2006/zhihu-plus-plus](https://github.com/zly2006/zhihu-plus-plus)（4.4k⭐、周更）——它若出现签名相关 commit，即知乎算法有动静；另留意 RSSHub `x-zse-96-v3.ts` 是否出现非格式化提交。
4. **真正要盯的是 `__zse_ck`**：2024+ 持续迭代的风控层（混淆 VM + WASM PoW + IP 声誉）。浏览器方案天然覆盖，但若未来想引入轻量通道，HGXY2004/zhihu-proxy 的 `lib/zseck.mjs`（vm 沙箱求真 PoW 值）是目前唯一公开的非浏览器解法参考。
5. **不建议**现在切换到逆向路线为主力：收益（省浏览器资源）明确但有限，风险（v3/v4 变体裂痕已说明服务端容忍度在收窄）不可控。
